# オリジナル武器 — 利用者の GLB をフォロワー専用の武器にする

ステータス: 実装中 (2026-10-25 起草、同日まはーが実装を承認)。

## 出てくる名前

- GLB: 3D モデルの標準形式 glTF を、テクスチャまで含めて一つのファイルにまとめた形式。利用者が用意する武器のモデルはこの形式で受け取る。VRM も中身は GLB である。
- PBR テクスチャ: glTF で質感を表す画像の組。色・金属らしさ・表面の粗さ・表面の凹凸 (法線マップ) を表す。
- NIF: Skyrim の 3D モデルのファイル形式。
- DDS: Skyrim がテクスチャに使う画像のファイル形式。
- ESP: Skyrim の MOD の追加データファイル。武器や NPC などのデータ一件ずつのまとまり (レコード) が入っている。
- FormID: ESP の中のレコード一つ一つに付く識別番号。
- Editor ID: レコードに付く識別名 (`SteelSword` など)。
- マスター: ESP が参照する元のデータファイル (`Skyrim.esm` や DLC のファイル)。
- 体型合わせ: 公式の防具をフォロワーの体型に合わせて変換する、このツールの既存の機能 ([armor-fitting.md](armor-fitting.md))。
- 付呪: Skyrim の日本語版での「エンチャント」の訳語。武器に魔法の効果を付けること。杖は付呪で魔法を撃つ。
- xEdit: Skyrim のレコードを閲覧・編集する外部ツール。VRM2Skyrim は xEdit のレコードの定義に従ってデータを読み書きしている ([FORMAT.md](../FORMAT.md))。

## 何をするか

利用者が用意した武器の 3D モデル (GLB) を、フォロワーが最初から持っている専用の武器にする。武器の種類はウィザードで選ぶ。持ち方・構え・振ったときと当たったときの音・攻撃力などの性能は、利用者が選んだ公式の武器から受け継ぎ、見た目のモデルだけを GLB から作ったものに差し替える。

動機は、SAIVerse のペルソナが自分の体 (VRM) と一緒に、自分のために作った武器を持ってスカイリムを歩けるようにすること (まはーの言葉)。最初に変換を試す入力ファイルは、まはーが用意した `aifi-crescent-staff.glb` である。3D 生成サービスの Tripo で作り、Tripo のリトポロジー (ポリゴン数を減らして作り直す機能) を通した杖で、三角形ポリゴン数 19,999・頂点数 25,540、PBR テクスチャを 3 枚持っている。

性能を公式の武器から写すのは、持ち方・音・攻撃力の値をこのツールが推測で書かずに済むようにするためである (書き手の提案)。このツールは Perk と魔法の FormID を推測せずゲームのレコードから引き ([follower-wizard.md](follower-wizard.md))、Editor ID もインストールされた `Skyrim.esm` から解決している ([FORMAT.md](../FORMAT.md))。武器の値も同じ考え方で実データから取る。

## まはーが決めたこと (2026-10-25)

この文書のうち、次の項目はまはーが会話の中で決めた。ここに無い項目は、書き手 (メティス) の提案である。

- 武器のモデルは GLB で受け取る。Tripo で作ることを前提にし、Blender で加工してから持ち込む利用者も想定する。
- 武器の種類は、ウィザードの画面で選べるようにする。
- 公式の武器を元にして性能を受け継ぎ、モデルだけを GLB から作ったものに差し替える。
- 握る位置と大きさは、ウィザードの画面でプレビューを見ながら調整できるようにする。
- ポリゴン数の自動削減は入れない。
- 弓とクロスボウは最初は対象外にする。
- 性能 (攻撃力など) を変更できる機能は欲しいが、ゲームにオリジナル武器を出せることを確かめてから検討する。
- 最初に試す `aifi-crescent-staff.glb` は、三角形ポリゴン数 19,999 のまま使う。公式の武器 (三角形ポリゴン数 366〜2,066) より細かいので重くなる可能性はあるが、まずゲームに出せることを確かめる。

## 受け取る GLB ファイルの条件

- 受け取る形式は GLB だけにする。既存の変換処理では Blender の glTF 読み込み機能 (`convert_blender.py` の `bpy.ops.import_scene.gltf`) を使っているので、武器も同じ仕組みで読み込める。GLB はテクスチャと材質の割り当てを一つのファイルに持つので、画像のパスが切れる事故が起きない。Blender で加工したい利用者も、Blender の「glTF 2.0 (.glb)」書き出しで同じ入口を通れる。FBX は受け取らない。
- GLB はウィザードの画面からアップロードする。今のアップロード処理 (`wizard.py` の `upload`) では拡張子 `.vrm` しか受け付けないので、GLB 用の受け口を別に足し、受け取ったファイルを `workspace/inputs/` に置く。
- 材質は glTF の PBR テクスチャを読む。Skyrim 用への変換は「テクスチャ」の節に書く。
- 入力ファイルの大きさ・原点・向きはそのまま使わない。Tripo で出力したモデルは、形全体の大きさが約 1 に揃っていて、原点が下端に置かれていた (実測: 高さ 0.98、原点は杖の下端、握る位置の情報は無い)。だから全長と握る位置はウィザードで決める (「握る位置と大きさ」の節)。
- 頂点の多いモデルは、既存の変換処理と同じく、間引かずに面で分割する。既存の書き出し処理では、`blender_meshes.py` の `partition_shape` を使って、部品一つの頂点と面の角 (Blender の loop) の数を 60,000 以下に分けている。Skyrim のモデルの部品 (`BSTriShape`) 一つに入る頂点は 65,535 個までで、既存の検査 (`armor_validation.py`、`validate.py`) でもこの上限で確かめている。ポリゴン数そのものを減らす処理は入れない。そのかわりウィザードで、読み込んだ GLB の三角形ポリゴン数と頂点数を表示し、公式の武器よりずっと多いことが分かるようにする。
- GLB に材質が複数あるときは、既存の変換処理 (`convert_blender.py`) と同じく材質ごとに部品を分けて、一本の武器としてまとめる。

## ウィザードでの選び方

STEP 03 の「開始武器」の欄に、「公式の武器」と「オリジナル武器」の切り替えを足す。「公式の武器」は今の動き (`settings.weapon` で選んだ公式武器を所持品に入れる) のまま変えない。「オリジナル武器」を選ぶと、次の五つを決める。

1. GLB ファイル。
2. 武器の種類。片手剣・短剣・片手斧・メイス・両手剣・両手斧・戦槌・杖の八つから選ぶ。種類は、公式の武器の `DNAM` の先頭にあるアニメーションの型と、`WeapType` で始まるキーワード (`KWDA`) の組で判定する。`Skyrim.esm` を数えると、片手剣は型 1 と `WeapTypeSword`、短剣は型 2 と `WeapTypeDagger`、片手斧は型 3 と `WeapTypeWarAxe`、メイスは型 4 と `WeapTypeMace`、両手剣は型 5 と `WeapTypeGreatsword`、両手斧は型 6 と `WeapTypeBattleaxe`、戦槌は型 6 と `WeapTypeWarhammer`、杖は型 8 と `WeapTypeStaff` の組だった。両手斧と戦槌はアニメーションの型が同じで、キーワードだけが違う。種類は候補を絞るためだけに使い、レコードに書き込む値はすべて元にする公式の武器から写す。弓とクロスボウは対象外にする。公式の弓はモデルの中に、弦を引く動きのための骨 (`Bow_StringBone1` など) を持っていて (`SteelBow.nif` で実測)、生成したモデルにその骨を付ける処理が別に要るからである。
3. 元にする公式の武器。選んだ種類の武器だけを候補に出す。候補は `Skyrim.esm` の武器のうち、名前を持ち、プレイヤーが手にできない設定になっていないものに限る。種類ごとに既定の候補を一つ決めておく (片手剣なら `SteelSword` のように、各種類で最も基本的な公式武器。杖の既定は実装時に候補を見て決める)。
4. ゲームでの表示名。
5. 握る位置・全長・向き。手に持たせたプレビューを見ながら決める (次の節)。

役割のプリセットを当てても、オリジナル武器の切り替えと選んだ内容は上書きしない。プリセットを当てたときに書き換えるのは、今と同じく「公式の武器」の欄の値だけにする。戦闘スタイルにも同じ決まりがある ([custom-combat-style.md](custom-combat-style.md))。

新しく足す画面の文言は、日本語と英語の両方で用意する ([wizard-localization.md](wizard-localization.md))。

## 握る位置と大きさ

公式の武器のモデルを開いて、次の決まりを実測で確かめた。モデルはゲームのアーカイブファイル (BSA) から取り出し、このツールが NIF の読み書きに使っているライブラリ PyNifly で測った。数字は Skyrim の長さの単位で、一般に 1 単位は約 1.43 cm とされる。

- 武器の長い向きはモデルの +Y で、原点が手で握る位置にある。
- 鋼鉄の剣 (`SteelSword.nif`): Y は −11.8 (柄頭) から 70.2 (切っ先) まで。
- 鋼鉄のメイス (`SteelMace.nif`): −13.9 から 48.3 まで。
- 鋼鉄の両手剣 (`SteelGreatSword.nif`): −21.1 から 93.0 まで。
- 竜司祭の杖 (`DragonPriestStaff3rd.nif`、`StaffIncinerate` の見た目): −69.6 から 64.4 まで。
- フォースウォーンの杖 (`ForswornStaff.nif`): −53.2 から 67.5 まで。杖は中ほどを握る。

既定の置き方は次のとおり。GLB の座標軸 (X・Y・Z) のうち、モデルを包む直方体の辺がいちばん長い軸を、武器の長い向きとみなす。その軸を Skyrim の +Y に合わせ、GLB でその軸の値が小さい側の端を「下端」(−Y の端) とする。全長は元にする公式の武器の全長に合わせ、握る位置も元にする公式の武器と同じ割合の所に置く。たとえばフォースウォーンの杖を元にすると、全長は 120.7、握る位置は下端から約 44% の所になる。

ウィザードでは、握る位置 (下端からの割合)・全長・上下の反転・長い向きを軸にした回転 (刃がどちらを向くか) を変えられる。

武器のプレビューは、ウィザードの途中でプレビュー画像を作る新しい処理として作る。ウィザードには、変換の前にプレビュー画像を作る処理の前例として、外見のプレビュー (`source_preview`) と頭のプレビュー (`head_preview`) がある。武器のプレビューは、テクスチャ付きの武器を、フォロワーが抜いて手に持った姿と、収めた姿の二枚で描く。値を変えたら描き直す (動かしながら連続で描き変えるものではない)。今の `render_blender.py` では、攻撃のアニメーション (`--animation attack`) のときだけ、`settings.weapon` の指定にかかわらず、`WEAPON` ノードの初期の位置 (アニメーションを付ける前の位置) と右手の姿勢から鋼鉄の剣の位置を合成し、仮の金属の材質で描くようになっている。手の位置を合成する計算は使えるが、テクスチャ付きの描画と収めた姿は新しく作る。

## モデルの書き出し

- 書き出す NIF は、公式の武器と同じく、一番上の親ノードを `BSFadeNode` にして、その下に部品の `BSTriShape` を置く形にする。
- 一人称視点のモデルにも同じ NIF を使う。公式の武器には一人称用に別のファイルを持つものが多いが、形は三人称とほぼ同じで (三角形ポリゴン数が多いものはある)、位置と大きさは三人称と一致していた (鋼鉄の剣・メイス・両手剣・二本の杖で実測)。公式の狩猟用の弓では、一人称用のレコードにも三人称と同じ `SteelBow.nif` が指定されている。
- 公式の剣とメイスは、鞘のモデル (`Scb`) を同じ NIF の中に持っている。オリジナル武器では鞘を作らない。剣を腰に収めると、抜き身のまま腰に下がる見た目になる。
- 公式の武器には、弓を除いて当たり判定のデータ (`bhkCollisionObject`) が入っている。地面に落とした武器が床で止まるのはこのデータがあるからなので、オリジナル武器にも当たり判定を付ける。公式の武器の当たり判定は、`bhkCollisionObject` (flags 129) の下に `bhkRigidBody` (衝突の層 5、motionSystem 3、qualityType 4、重さは鋼鉄の剣で 10、フォースウォーンの杖で 9) を置き、形を `bhkConvexVerticesShape` (モデルの外側を大まかに包む形 (凸包)。頂点 12〜19 個) にしていた (竜司祭の杖だけは `bhkCapsuleShape`)。オリジナル武器では、`bhkRigidBody` の値は元にする公式の武器のものをそのまま使い、形はオリジナル武器のモデルから作った凸包を、頂点数を公式の武器と同じくらい (数十個以下) に減らして入れる。PyNifly はこの形を書き出せる (Blender からの書き出しは `export_bhkConvexVerticesShape`、Blender を通さない書き出しは `add_collision` と `add_shape`)。
- ファイルは `meshes/<asset_dir>/weapon.nif` と `textures/<asset_dir>/weapon*.dds` に置く。`asset_dir` はフォロワーごとに違うので、複数のフォロワーの MOD を同時に入れてもファイルが衝突しない ([package-coexistence.md](package-coexistence.md))。既存のファイル名 (`avatar`・`skeleton`・`garment_*`・`fitted_*`・`tex_NNN_*`・`flat_n` など) とも衝突しない。

## テクスチャ

glTF の PBR テクスチャを、公式の金属の武器と同じ組み合わせの画像に変換する。公式の鋼鉄の剣・メイス・両手剣は、色 (`SteelSword.dds`)・表面の凹凸を表す法線マップ (`SteelSword_n.dds`)・周囲の映り込みをどこに出すかを決めるマスク (`SteelSword_m.dds`) の三枚に、映り込む景色の画像 `textures\cubemaps\ShinyDull_e.dds` を組み合わせていた (実測)。公式の杖は色と法線マップの二枚だけだった。

材質が一つなら名前は `weapon.dds`・`weapon_n.dds`・`weapon_m.dds` にする。材質が複数あるときは、GLB の材質の番号を付けて `weapon_0.dds`・`weapon_0_n.dds` のようにする。

- 色 → `weapon.dds`。glTF の `baseColorFactor` は、既存の決まり ([base-color-factor.md](base-color-factor.md)) と同じく、RGB だけを線形の色空間でテクスチャに焼き込む。
- 表面の凹凸 (法線マップ) → `weapon_n.dds`。緑チャンネルは反転せずにそのまま写す。glTF の決まりでは緑チャンネルは上向き (OpenGL 式) で、Skyrim は逆向き (DirectX 式) だと言われることがあるが、画像を測ると両者は同じ向きに読めた。測り方は、法線マップから表面の傾きを計算し、本物の凹凸から作った画像なら傾きのつじつまが合う (渦の成分がゼロに近くなる) ことを使って、緑の向きを二通りに仮定して比べた。公式の `SteelSword_n.dds`・`ForswornStaff_n.dds`・`SteelMace_n.dds` と、Tripo の法線マップのどれもが、同じ側の仮定でつじつまが合った (2026-10-25 実測)。ただし差は 8〜28% と大きくないので、ゲームで凹凸の陰影が逆に見えたら、緑を反転する。反転するかどうかはコードの一か所にまとめ、そこだけ変えれば切り替わるようにする。
- 粗さ → `weapon_n.dds` のアルファチャンネル。glTF では、金属と粗さの画像の G チャンネルが粗さ、B チャンネルが金属で、`roughnessFactor` と `metallicFactor` をそれぞれ掛けた値が実際の値になる。Skyrim ではこのアルファの値が光沢の強さとして扱われるので、粗さを反転した値を入れる。
- 金属 → `weapon_m.dds` (映り込みの範囲を決めるマスク)。金属の値が 0.5 以上の画素が全体の 1% 以上あるときだけ、マスクを作って、映り込む景色の画像に `ShinyDull_e.dds` を指定する。この線は最初の杖で見た目を確かめて調整する。
- DDS への変換は、既存の変換処理である `textures.py` の `convert_textures` を通す。DDS の寸法の決まり ([dds-dimensions.md](dds-dimensions.md)) はここで適用される。今の `convert_textures` では、法線マップ以外のすべての画像が sRGB として変換されるので、色ではなくマスクである `weapon_m.dds` は sRGB として扱わないように変える。
- `ShinyDull_e.dds` はフォロワーの ZIP に同梱せず、ゲーム本体のアーカイブにある公式のファイルを使う。既存の決まり ([equipment-texture-reuse.md](equipment-texture-reuse.md)) と同じく、アーカイブの名前・パス・SHA256 を記録して、検査 (`validate.py`) で「ZIP に同梱しないゲーム本体の公式ファイル」として認める。
- glTF の拡張機能による見た目の効果は再現しない。今回テストに使った Tripo 製の GLB では、`KHR_materials_specular` と `KHR_materials_volume` が使われていた。

## レコード (ESP)

元にする公式の武器の `WEAP` レコードをコピーし、フォロワーの ESP の中に専用の FormID で置く。

- 差し替える項目: `EDID` (`settings.prefix + "OriginalWeapon"`)、`FULL` (表示名を文字列で入れる)、`MODL` (新しい NIF のパス)、`WNAM` (一人称のモデル。下の専用の `STAT` レコードを指定する)、`OBND` (新しいモデルの大きさから計算し直す)。`MODT` は消す。
- `DESC` (説明文): `Skyrim.esm` の武器の `DESC` は、4 バイトの文字列 ID になっている (`SteelSword` で実測)。フォロワーの ESP は文字列の表を持たない形で作っているので、ID のままコピーすると別の値として読まれる。既存の防具の処理 (`armor_patch.py`) と同じく、ゲームの文字列の表から文字列に直して入れる ([FORMAT.md](../FORMAT.md) の「Localized names/descriptions are resolved into inline strings」)。
- `CNAM` (テンプレートの指定) は外す。公式の付呪つきの武器と杖には、`CNAM` に別の武器が指定されている (`StaffIncinerate` は `StaffTemplateDestruction` を指定している)。`CNAM` を残したままモデルを差し替えると、ゲームがテンプレート側のモデルを表示する可能性がある。外しても値は失われない。`Skyrim.esm` で `CNAM` を持つ武器 2,210 件をテンプレートと比べると、全件が自分のレコードの中に値を全部持っていて、テンプレートと違うのは `EDID`・`FULL`・`CNAM`・`EITM`・`EAMT`・`DATA` (246 件)・`OBND` (38 件) だけだった。`MODL` は全件テンプレートと同じだった (2026-10-25 実測)。だから `CNAM` を外すだけでよく、テンプレートから値を書き写す処理は要らない。
- コピーしたまま残す項目: 上に挙げた `EDID`・`FULL`・`MODL`・`WNAM`・`OBND`・`MODT`・`DESC`・`CNAM` 以外の全部。種類と性能 (`DNAM`、`DATA`、`CRDT`)、装備する手 (`ETYP`)、防いだときの音と衝撃 (`BIDS`、`BAMT`、`INAM`)、キーワード (`KWDA`)、各種の音、杖の付呪 (`EITM`、`EAMT`) を含む。
- 一人称のモデル用の `STAT` レコードは、元にする公式の武器の `WNAM` に指定された公式の `STAT` をコピーして作る。`EDID` を `settings.prefix + "OriginalWeapon1stPerson"` に、`MODL` を新しい NIF のパスに、`OBND` を新しいモデルから計算し直した値にし、`MODT` を消す。`DNAM` (材質と角度の設定) はコピーしたまま残す。
- 専用の FormID は、`WEAP` を `0x8D0`、`STAT` を `0x8D1` にする。コード中の自前の FormID を数えると、`0x800` から `0x880` までの間に、既存のレコードで使っている番号と予約している番号が散らばっている。`0x880`〜`0x8BF` は、`armor_patch.py` で旧形式の体型合わせ用として扱われる範囲である。`0x8C0`〜`0x8FF` を使っている箇所は無かった。自前の FormID の割り当て表は今どこにも書かれていないので、実装のときに [FORMAT.md](../FORMAT.md) に割り当て表を作り、この二つを載せる。
- マスターの番号の付け替え: 体型合わせを使うと、フォロワーの ESP のマスターに DLC のファイルが足される (`build_npc.py` の `extra_masters`)。そのとき、自前のレコードを指す FormID のうち、`follower_plugin.py` の `REFS` に載った項目だけが付け替えられる。新しい `WEAP` の `WNAM` は自前の `STAT` を指すので、元にする公式の武器を `Skyrim.esm` に限っても、`REFS` に `WEAP` の `WNAM` を足す必要がある。`WEAP` と `STAT` の `MODL` はファイルのパスの文字列なので、`REFS` に足してはいけない (`ARMO` の `MODL` は FormID なので載っている。同じ名前で中身が違う)。最終検査 (`plugin_validation.py`) の参照の検査にも、`WEAP` の `WNAM` と、所持品に入れた新しい武器を足す。
- オリジナル武器を一本、フォロワーの所持品 (`CNTO`) に入れる。オリジナル武器を選んでいるときは、`settings.weapon` の公式武器を所持品に入れない。`settings.weapon` の値は設定に残す (公式の武器に戻したときに使う)。`game_catalog.py` の `validate_settings` では、公式の武器を選んでいるときだけその値を検査する。
- 最終検査 (`plugin_validation.py`) では自前のレコードの数を厳密に照合しているので、オリジナル武器を選んだときの 2 件 (`WEAP` と `STAT`) を、期待する数に足す。
- 元にする公式の武器は、最初は `Skyrim.esm` の武器に限る。DLC の武器を元にするには、二つを片付ける必要がある。一つは、`GameCatalog` で候補を読み込む対象が今は `Skyrim.esm` だけになっていること。もう一つは、`WEAP` の中の DLC への参照を内部の番号に直す処理 (`armor_patch.py` や `official_catalog.py` にあるのと同じ種類の処理) が要ること。
- 公式の武器のレコードは上書きしない。

## 設定

選んだ内容は、既存の設定 JSON (`settings.py` の `FollowerSettings`) に項目を足して保存する。`FollowerSettings.from_dict` では、定義されていない項目があると読み込み時にエラーになるので、項目は `settings.py` に定義してから使う。

- `weapon_mode`: `"official"` か `"original"`。既定は `"official"` で、今までの設定はこの値として読む。
- `original_weapon`: オリジナル武器を選んだときだけ持つ。中身は次のとおり。
  - `sha256`: GLB の SHA256。
  - `filename`: アップロードしたときのファイル名 (表示用)。
  - `kind`: 武器の種類。`sword`・`dagger`・`waraxe`・`mace`・`greatsword`・`battleaxe`・`warhammer`・`staff` のどれか。
  - `base`: 元にする公式の武器の Editor ID。
  - `name`: ゲームでの表示名。
  - `grip`: 握る位置。下端から測った、全長に対する割合で、0 より大きく 1 より小さい数。
  - `length`: 全長。Skyrim の長さの単位で、0 より大きい数。
  - `flip`: 上下を反転するかどうか (`true` または `false`)。
  - `roll`: 長い向きを軸にした回転の角度 (度)。0 以上 360 未満。

GLB の場所は設定に保存しない。設定 JSON は配布 ZIP に同梱され (`converter.py`)、VRM も SHA256 だけで結び付けている (`appearance_source_sha256`)。オリジナル武器も同じく、再変換のときは利用者が同じ GLB を選び直し、SHA256 が一致することを確かめる。

## 最初は対象外にするもの

弓とクロスボウ、盾 (盾は防具の側の機能)、一人のフォロワーに複数のオリジナル武器を持たせること、DLC の武器を元にすること、ポリゴン数の自動削減、性能 (攻撃力など) の変更、付呪の変更、鞘、刃に付く血の表現 (公式の剣の `EdgeBlood`)。性能の変更は、ゲームにオリジナル武器を出せることを確かめたあとで検討する。

## ゲームの中で確かめること

NPC は、所持品の中から自分で装備する武器を選ぶ。オリジナル武器の性能は元にする公式の武器と同じなので、プレイヤーがもっと強い武器を渡すと、フォロワーが持ち替えるかもしれない。また、フォロワーの戦闘のクラスや戦闘スタイルと武器の種類が合っていないときに、フォロワーがその武器を使うかどうかは分かっていない。どちらもゲームで確かめ、必要ならウィザードで注意を出す。

## 検証

- 書き出した NIF をもう一度読み込んで、長い向きが +Y であること、原点が設定した握る位置にあること、全長が設定どおりであること、部品ごとの頂点数が 65,535 以下であること、テクスチャのパスが ZIP の中のファイルか記録済みの公式のファイルを指していること、当たり判定のデータがあることを確かめる。
- 書き出した ESP をもう一度読み込んで、次を確かめる。コピーした `WEAP` レコードが、差し替えた項目と外した項目以外は元にする公式の武器と同じであること。`MODL` と、`WNAM` で指定した `STAT` レコードの `MODL` の両方に同じ NIF が指定されていること。`DESC` が文字列になっていること。フォロワーの所持品に入っていること。DLC のマスターが足された設定でも、`WNAM` が自前の `STAT` を指していること。
- 最終検査 (`plugin_validation.py`) を、オリジナル武器ありとなしの両方の設定で通す。
- 武器を抜いた姿と収めた姿のプレビュー画像を、ウィザードから作れることを確かめる。
- 公式の武器のレコードと、公式のファイル (モデル・テクスチャ) が変わっていないことを確かめる。
- 設定 JSON の書き出しと読み込みで、オリジナル武器の設定が保たれること、役割のプリセットを当てても消えないことを確かめる。
- 実際の入力ファイル `aifi-crescent-staff.glb` を使って、ウィザードの操作から ZIP の出力まで一通り動かす。
- ゲームでの表示、武器を抜く・収める・振る動き、杖なら魔法を撃てること、地面に落として床で止まることは、まはーがゲームで確かめる。それまでは、ゲームでの動作を確認済みとして扱わない。
